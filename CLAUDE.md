# Training App

## Training Workflow architecture (2026-07 merge)

`training_projects` is the spine of the whole workflow — **the project IS the approval request**. The old `training_requests` / `request_attendees` / `request_schedule` / `registration_attendees` tables were merged away (one-time rebuild migration in `server/db/db.js` detects the old shape via the `request_id` column and drops/recreates the workflow tables; Setup master data is untouched).

Key invariants:
- **Project = ใบขออนุมัติ**: `training_projects` carries `req_no` (auto `TR-<year>-NNN`), dates, budgets, objective, and `approval_status` (recorded manually by HRD via `PATCH /training-projects/:id/approval` — there is no in-app approver role/login).
- **One participant list per project**: `project_participants` is the single source read by the availability matrix, registration sheet (`training_registrations` is header-only; check-in lives on `project_participants`), and evaluation. Never create a second per-phase attendee table.
- `participant_count` is **computed** (`COUNT(project_participants)`) in `server/routes/training-projects.js` queries — there is no stored column; don't add one.
- **All workflow tool pages live under `/development/workflow/:projectId/*`** nested in `ProjectShell.jsx` (loads project + status once, provides them via `useProject()` outlet context, renders the persistent header + phase bar). Satellite `route` values in `client/src/config/workflowHubs.js` are relative segments, not absolute paths.
- **Satellite order (2026-07 usability pass)**: Phase 1 chain is `participants → availability → vendor_check → invoice_intake → pr_issuance/memo_issuance` — รายชื่อผู้เข้าอบรมเป็นโหนดแรกเพราะทุก phase อ่านรายชื่อกลางชุดนี้ (participants is **not** `publicHidden`). Phase 2 is `schedule → registration`; the `schedule` route is now the combined Node **โครงร่างและกำหนดการอบรม** (Step 1 โครงร่างอบรม, Step 2 กำหนดการอบรม) before printing registration. The availability matrix **auto-unions `project_participants`** into its participant rows server-side (`GET /availability/:projectId`) — no second add step, no phantom seed slots; participants are managed only on the participants page (the matrix keeps add-modals for instructors/venues only).
- **Invoice intake (AI pipeline)**: `POST /api/invoices/extract` (multipart, PDF/JPG/PNG/WebP ≤ 10MB, `project_id` field) → Claude `claude-opus-4-8` with adaptive thinking + structured outputs (`output_config.format` json_schema in `server/routes/invoices.js`) → row in `invoice_extractions` (project_id nullable; project delete unlinks it like the PR ledger). Extracts เลขที่ Invoice, ผู้ขาย, line items (qty/unit/unit_price/amount), ยอดเงิน, **`due_date` = วันที่ต้องทำจ่าย**; `uncertain_fields` + a subtotal self-check highlight low-confidence fields in the review UI. API key = `ANTHROPIC_API_KEY` in root `.env`; **a missing key must never crash boot** — `server/lib/anthropic-client.js` is lazy, `/extract` returns 503 `AI_NOT_CONFIGURED`, and `InvoiceIntakePage` falls back to manual entry (`POST /api/invoices/extractions`, saved directly as `confirmed`). `GET /api/invoices/status` tells the UI whether AI is configured. AI results start `pending` and must be human-confirmed (`PATCH .../:id/confirm`) before they count anywhere.
- **Confirmed invoices prefill PR + Memo**: `PRIssuancePage`/`MemoIssuancePage` fetch the project's confirmed extractions and pass an `invoices` prop — PRForm fills the 10-row item grid + required_date (earliest due date), MemoForm builds budget_items (1 invoice = 1 item with vendor/invoice_no/due_date/amount, replacing the 5-budget-category seed when invoices exist). Invoice satellite color: `status.invoice.confirmed>0` = done, `count>0` = warning.
- **Memo export auto-advances approval**: exporting a Memo under a project whose `approval_status` is `draft` PATCHes it to `pending` (in MemoForm) — the memo satellite color derives from approval_status, so it moves without a manual step.
- Phase advancement is manual with soft warnings (`GET /training-projects/:id/status` powers them); never hard-block step changes. When the current phase has no warning, StepNavigator shows a green "งานหลักของขั้นนี้ครบแล้ว" nudge; the approval card also lists exactly which Training-Proposal fields are still missing (all projects, not just DSD).
- Project creation is course-first: pick a course from Setup, name auto-fills, `req_no` auto-issues. CoursePlan/TrainingRequest left-nav pages were deleted.
- **โครงร่างและกำหนดการอบรม (Phase 2 `schedule` route)**: `SchedulePage.jsx` is a two-step Node. Step 1 edits the Training Proposal outline fields on `training_projects` (name, dates, location, trainer, objective, target group, quantitative/qualitative assessment) and validates required outline fields before Step 2. Step 2 edits `project_schedule` rows + `schedule_*` settings columns on the project. Date mode and training dates are chosen in Step 1 only; Step 2 treats dates as read-only source data. `GET /training-projects/:id/schedule` returns saved rows, or seeds (unsaved, `seeded: true`) from the course's topics; time computation stays client-side in `client/src/lib/coursePlanUtils.js` (`computeSchedule`) — don't duplicate it server-side. `start_date` comes from `training_date`, which Step 1 or the availability ranking's "ใช้วันนี้เป็นวันอบรม" button sets.
  - **หัวข้อย่อย**: newline-separated TEXT (1 line = 1 bullet) on **both** `training_topics.subtopics` (Setup master — seeds into new project schedules) and `project_schedule.subtopics` (per-project copy, editable without touching Setup). Rendered as bullets under the topic name in the schedule PDFs.
  - **พักเที่ยง**: `schedule_lunch_start`/`schedule_lunch_end` on the project (default 12:00–13:00; empty string = disabled). `computeSchedule` skips the lunch window in `single`/`consecutive` modes (a topic crossing lunch start gets its end pushed by the lunch duration); `withBreakRows` injects display-only `{ is_break: true }` rows for the UI table and PDFs. `separate` mode ignores lunch.
- **AI PDF intake guidance**: agents that read instructor PDFs for this Node must use `docs/ai-agent-training-pdf-guide.md`. The implementation spec lives in `docs/training-outline-schedule-spec.md`. Step 1 intentionally has no "หลักการและเหตุผล"; objectives and assessment methods must be checked for consistency.
- **Company-format documents = real Office templates filled server-side, downloaded as docx/xlsx** (2026-07 decision: **no LibreOffice on the server, ever** — users install LibreOffice/Word on their own machines and print/convert to PDF themselves, so everything works on Vercel; all soffice `export-pdf` routes were deleted). Training Proposal + กำหนดการ use `server/templates/proposal_pack_template.docx` (2 pages, button on WorkflowDetailPage) and `schedule_template.docx` (schedule only, button on SchedulePage — for the future DSD bundle). Both are **generated from the company original** `proposal_source.docx` by `node server/scripts/build-proposal-templates.mjs` — if the company sends a new original, replace the source and re-run; never hand-edit the generated templates. Fill route `server/routes/projectDocs.js` + `server/lib/renderProposalDocx.js`; the client POSTs the computed schedule (`buildDocExportPayload` in `coursePlanUtils.js` — grouping rows per day incl. break rows; `computeSchedule` stays client-side per the invariant above). Multi-day = one date-headed table per day (`{#days}` loop; the original's floating table was converted to inline on purpose so it can repeat); single-day renders identical to the original. Budget block = 5 lines exactly per the company form, `-` when 0, **no รวมทั้งสิ้น line** (settled decision). Course name on these docs = project name, falling back to course name. **Registration sheet is xlsx-only** via the `registration_template.xlsx` pipeline (`server/lib/renderRegistrationXlsx.js`, `POST /api/registration/export-xlsx`): one tab per training day (project `training_date`–`end_date`), "(ต่อ)" continuation tabs with renumbered No. column when a day exceeds the form's 28 rows. The old jsPDF mimics (`exportProposalPack`, `exportSchedulePdf`, `exportRegistrationSheet`, `exportEvalSummary`, and the dead memo/PR/DSD variants) were deleted — `pdf-generator.js` now holds only the internal `exportProjectSummary`.
- **PR ↔ project**: `purchase_requisitions.project_id` (nullable) is set when PRForm is opened under a project. Ledger rows are never deleted — project deletion unlinks them (`UPDATE ... SET project_id=NULL` in the delete route; old ALTER-added columns lack `ON DELETE SET NULL`, so keep that explicit unlink).
- Satellite colors on `HubSatelliteGraph` derive from `GET /training-projects/:id/status` (done/warning/none per satellite); memo status is inferred from `approval_status` — there is no memo table. MemoForm/PRForm accept optional `project` + `invoices` props that prefill subject/budget items (memo) and reason/items (PR).
- **Project classification**: `competency_type` (organizational=everyone / functional=per-department / leadership=supervisors+) defaults from the course's own `competency_type` at creation; `delivery_type` (`inhouse`/`public`). Labels/colors/badges live in `client/src/config/projectTypes.jsx` — use those, don't restyle ad hoc. **Public** projects (employee sent to an external course, company just pays): satellites flagged `publicHidden` in `workflowHubs.js` (availability, vendor_check, registration, schedule) are hidden from the graph and phase bar, the Phase-2 registration advance-warning is skipped, and `POST .../records` treats every participant as attended (no check-in exists). A hidden satellite's children auto-become roots — `getSatelliteOffsets` already tolerates missing parents.
- **ยื่น ยป. กรมพัฒนาฝีมือแรงงาน tracker**: shows only when the project's course has `send_to_dsd` (Setup flag). Deadline = `dsd_deadline` override, else `training_date − 30 days` (computed in `dsdDeadline()` exported from `server/routes/training-projects.js`, UTC-pure to avoid TZ day-shift). Checklist = 2 auto items (`proposal_ready`: objective+target_group+location+at least one การวัดผล field; `schedule_ready`: ≥1 `project_schedule` row) + 2 plain manual checkboxes (`dsd_submitted`, `dsd_approved` — user decided no dates/ref-no; the ยื่น happens manually on the DSD website, the app only tracks it). Lives in the `dsd` block of `GET /:id/status`, rendered as `DsdChecklistCard` on WorkflowDetailPage; `GET /dashboard/stats` returns `dsdAlerts` (unsubmitted, future training date, deadline ≤ 21 days away or overdue) shown as an amber strip on the Dashboard. Soft reminders only — never blocks phase advancement.
- **Phase 4 (บันทึก-รายงาน)**: `POST /training-projects/:id/records` snapshots all participants into `training_records` (denormalized on purpose — history must survive later edits; hours from `project_schedule` falling back to course duration, result from latest evaluation) and auto-marks matching `employee_roadmaps` rows `completed` for checked-in employees. Re-POST replaces the project's whole record set (idempotent). `GET /training-projects/:id/summary` is the read-only aggregate that powers both SummaryReportPage and DSDExportPage; the internal PDF exporter (`exportProjectSummary`, the only jsPDF export left) lives in `client/src/lib/pdf-generator.js`.

## DSD report form (ฟอร์มรายงานผลกรมพัฒนาฝีมือแรงงาน)

Third template pipeline, xlsx-only (no PDF step). `server/templates/dsd_template.xlsx` is a **one-time LibreOffice conversion of the official government .xls** — the structure must never be altered (user: "ห้ามเปลี่ยนฟอร์มเด็ดขาด"); the original's VBA macro (officer's duplicate-check button) is lost in conversion, which the user confirmed is acceptable because `server/routes/dsd.js` performs the same checks (13-digit checksum + duplicate IDs) server-side before export and returns 400 with names on failure.

Layout facts (re-derive with `node server/scripts/inspect-dsd-xlsx.mjs` if the template is replaced — never guess):
- Users fill only sheet `Summary`, data rows **8–107** (100-person cap), row 108 is the form's own average row. Sheet `Data` is all formulas for DSD officials — never write to it.
- Per-row input columns: A=running no, B=national ID (text), C/D/E=title/first/last (title must be the full form นาย/นาง/นางสาว — the form derives gender from it), F=position, **G–K = 5 competency topics scored 0–3** (0=ไม่เปลี่ยนแปลง…3=ดีขึ้นชัดเจน), N=income band from dropdown `Summary!W28:W34` — always written as exactly `N/A (ไม่ระบุ)` per user decision, Q=`passed`/`fail` (lowercase; Data sheet converts to ผ่าน/ไม่ผ่าน), R=`ü` when passed. Columns **L/M/O/P hold per-row form formulas — clear/write only the input columns** (the fill route clears leftover sample data rows first).
- Topic defaults per person come from the project evaluation via `eval_items.dsd_topic` tags (Setup › หัวข้อประเมิน): average mapped scores per topic, then 5→3, 4→2, 3→1, else 0. Per-person overrides live in `project_dsd_assessments` (edited in the DSDExportPage grid); name split (splitThaiName) is auto but editable there.
- `employees.national_id` (Setup › ข้อมูลพนักงาน) is required for everyone in the file; only checked-in attendees are exported (public projects: all participants).

## Document generation (Office template pipelines)

Every company document is a real Office template filled server-side and downloaded as docx/xlsx — **there is no PDF conversion step anywhere on the server** (removed 2026-07; users open/print/convert locally with Word or LibreOffice). All pipelines live under `server/` and are mounted in `server/index.js`.

| | Memo | PR (Purchase Requisition) | Proposal + กำหนดการ | ใบลงทะเบียน |
|---|---|---|---|---|
| Template | `memo_template.docx` | `pr.xlsx` | `proposal_pack_template.docx` / `schedule_template.docx` (built from `proposal_source.docx`) | `registration_template.xlsx` |
| Fill engine | `docxtemplater` + `pizzip` | `ExcelJS` (literal cells) | `docxtemplater` + `pizzip` | `ExcelJS` (sheet-copy per day) |
| Fill code | `server/routes/memo.js` | `server/lib/renderXlsx.js` | `server/lib/renderProposalDocx.js` | `server/lib/renderRegistrationXlsx.js` |
| Routes | `POST /api/memo/export-docx` | `POST /api/pr/export-xlsx` | `POST /api/training-projects/:id/export-proposal-docx` · `/export-schedule-docx` | `POST /api/registration/export-xlsx` |
| Client caller | `MemoForm.jsx` | `PRForm.jsx` (also via `Development/PRIssuancePage.jsx`) | `WorkflowDetailPage.jsx` / `SchedulePage.jsx` (payload from `buildDocExportPayload`) | `Registration.jsx` |

PR intentionally uses ExcelJS/xlsx instead of docxtemplater: a spreadsheet's grid makes wrong-cell mistakes obvious, whereas a misplaced docx placeholder fails silently. Memo stays on docxtemplater/docx.

### PR cell mapping

`server/lib/renderXlsx.js` writes to fixed cell addresses on the single sheet `"PURCHASE REQUISITION (PR)"` in `server/templates/pr.xlsx`. These addresses were read off the real template with `server/scripts/inspect-pr-xlsx.mjs` (dumps every cell address, value, and merge range) — **re-run that script and update the addresses in `renderXlsx.js` if the template is ever replaced.** Never guess coordinates.

Key mapping:
- Header fields: `E5`/`I5` (PR No./Date), `E6`/`I6` (Department/Required Date), `E7`/`I7` (Requester/Expense Type). `I5`/`I6` are date-formatted cells — pass real `Date` objects.
- Item loop: rows `10`–`19` (10 fixed rows), columns `C`–`I` (GL Code, Item Code, Description, Qty, Unit, Unit Price, Amount).
- `I20`/`I21`/`I23` are pre-existing formulas in the template (subtotal, VAT, grand total) — left untouched; `workbook.calcProperties.fullCalcOnLoad = true` forces them to recalculate when opened. `I22` (WHT) is a plain value we write directly.
- `C26` — merged reason-for-request box.
- Signature block (`C34/C35`, `E34/E35`, `G34/G35`, requester/approver 2/approver 3): name and title only, no `ตำแหน่ง/ Position:` label prefix, all explicitly center-aligned (`C34` is merged with `D34` at fill time to match the width of `C35:D35`/`C36:D36` — the template doesn't merge it by default, which otherwise skews centering vs. the rows below it). Only the requester's column (`C36`) gets an auto-filled date; approver columns 2/3 keep their blank handwritten-date placeholder.

### Proposal/schedule template internals

`build-proposal-templates.mjs` locates paragraphs in the original by their sample text and throws if the layout changed — safe to re-run blind. docxtemplater options everywhere: `{ paragraphLoop: true, linebreaks: true }`. Template tags: proposal page uses `{course_name} {location} {date_label} {time_label} {participant_count}`, loops `{#objectives}`/`{#targets_rest}`/`{#quant_items}`/`{#qual_items}` (1 line of the TEXT field = 1 list item; `targets_first` rides on the label line), and 5 preformatted budget strings. Schedule page: `{#days}` wraps an optional `{#show_date}` heading + the table; row loop `{#rows}` spans both cells with `{#reg}` (bold topic + `{#subtopics}` bullets) vs `{#is_break}` (centered line cloned from the original lunch row) conditional blocks.
